# Diversity, novelty and process metrics for LLM-driven evolutionary code search

Scope: how diversity, novelty and search-process health are measured in LLM-driven and classical evolutionary program search; evidence linking them to search success; and which metrics can be computed from OpenEvolve 0.4.0 records. Current as of 2026-11-06. Sources were read on the web through fetch tools. Where only an abstract or a search-result summary was available, the entry says so.

## Key Question 1: Population-level diversity metrics, and the evidence on which ones correlate with success

### Takeaway
There are four families of measures. Genotypic measures look at code text, ASTs or embeddings. Phenotypic or behavioral measures look at output or behavior vectors. Quality-diversity measures look at the archive. Entropy and spectral measures (SWDI/CDI, Vendi) can be computed over either representation. The strongest evidence is old and new together: Burke et al. 2004 in classical GP and DivEval in 2026 in LLM evolution. Both say structural or source-level diversity and behavioral diversity separate, and that behavioral diversity is what matters. No single metric correlates reliably with success across tasks. The correlation changes with run stage, task and measurement level.

**Genotypic (code-level) measures**
- Classical GP surveys group diversity methods into lineage-based, genotype-based and phenotype-based approaches. They also note that candidates in artificial evolution tend to "homologize", unlike natural divergence. — [Squillero & Tonda 2016, Information Sciences 329:782–799 (repository record)](https://iris.polito.it/handle/11583/2622368)
- Burke et al. 2004 found that the correlation between diversity and fitness varies across stages of a run. They also found that "populations ... become structurally similar while maintaining a high amount of behavioural differences." — [GP bibliography abstract](https://gpbib.cs.ucl.ac.uk/gp-html/gustafson_2004_IEEE.html). The PPSN 2002 precursor reports that successful runs converge structurally while keeping high fitness diversity. — [Burke et al. PPSN 2002](https://gpbib.cs.ucl.ac.uk/gp-html/burke_ppsn2002_pp341.html)
- **TSED (AST edit distance):** Song et al. (ACL 2024 short paper) parse code with tree-sitter and compute APTED tree edit distance, normalized by the larger tree's node count, with a ramp function. Their tool covers 48 languages, C++ included. TSED correlated with BLEU and Jaccard, and strongly with GPT-judged similarity, on CoderEval Java and Python. — [arXiv 2404.08817](https://arxiv.org/html/2404.08817v2)
- **Line-diff ratio:** LLaMEA's parent–offspring "diff ratio" is the number of differing lines divided by the length of the longer program. GPT-4-driven LLaMEA showed the largest differences. This definition comes from a search summary of the LLaMEA paper, not a full-text read. — [arXiv 2405.20132](https://arxiv.org/pdf/2405.20132)
- **Shingle Jaccard:** HoliDivEvolve (arXiv 2610.38407, POSTECH and MSRA, v2 dated 30 Oct 2026) measures code redundancy lexically. It tokenizes the EVOLVE-BLOCK, normalizes comments and literals, and takes the Jaccard overlap of 5-token shingles. — [arXiv 2610.38407](https://arxiv.org/html/2610.38407)
- **Code embeddings:** HSEvo embeds code with CodeT5+ (110m-embedding) after stripping comments and docstrings through the AST and normalizing to PEP 8. — [HSEvo](https://arxiv.org/html/2412.14995). EvoDiverse uses mean pairwise cosine distance between CodeBERT embeddings for equation programs and TF-IDF embeddings for circle-packing code. — [arXiv 2606.10587 HTML](https://arxiv.org/html/2606.10587v1). ShinkaEvolve uses OpenAI text-embedding-3-small on the mutable code region. — [ShinkaEvolve](https://arxiv.org/html/2509.19349)
- **Code Evolution Graphs** (van Stein, Kononova, Kotthoff & Bäck, GECCO 2025) extract static AST features, build DAGs, and project them with PCA and t-SNE. Programs generated by LLaMEA and EoH show that different LLMs have different coding "styles". — [arXiv 2503.16668](https://arxiv.org/abs/2503.16668v1)

**Phenotypic / behavioral measures**
- **Semantic GP** treats semantics as "the set of output values of a program on the training data." Its methods divide into diversity, indirect-semantic and direct-semantic methods (Vanneschi, Castelli & Silva 2014, GPEM 15(2):195–214). — [GP bibliography](https://gpbib.cs.ucl.ac.uk/gp-html/Vanneschi_2014_GPEM.html)
- **FunSearch behavior clustering:** within each island, programs are clustered by signature, the tuple of scores on each input. Clusters are sampled by a Boltzmann distribution over score, with temperature T_cluster = T0(1 − (n mod N)/N). Within a cluster, shorter programs are favored. The authors relate signature clustering to quality-diversity, lexicase selection and fitness-uniform optimization. — [Romera-Paredes et al., Nature 2024](https://www.nature.com/articles/s41586-023-06924-6)
- **Functional distance on a fixed input grid:** the trajectory analysis of 15 LLMs on 8 tasks defines novelty as nov(a) = min over prior b of D_T(a, b). D_T is a functional behavior distance on a fixed input grid for equation discovery and heuristic design, edge-set distance for TSP, and embedding cosine for prompts. — [arXiv 2604.19440](https://arxiv.org/pdf/2604.19440)
- **Algorithm-behavior metrics:** the behaviour-space analysis of LLaMEA-generated optimizers logs exploration, exploitation, convergence and stagnation metrics for each candidate. It also builds behaviour-based Search Trajectory Networks. — [arXiv 2507.03605](https://arxiv.org/abs/2507.03605v1)
- **LLM-judged algorithm sameness:** Lee, Chon et al. cluster solutions by whether an LLM judges them algorithmically the same, then estimate the number of distinct algorithms. They report low algorithmic diversity in model-generated code. Combining models and using temperature above 1.0 raised diversity but could lower correctness. — [arXiv 2503.00691](https://arxiv.org/abs/2503.00691)

**Quality-diversity (archive) measures**
- **MAP-Elites:** Mouret & Clune compared MAP-Elites on four measures: global performance (the best solution), global reliability, precision, and coverage (the fraction of feature space filled). — [arXiv 1504.04909](https://arxiv.org/abs/1504.04909). The metric definitions come from secondary summaries; I did not read the full paper.
- **QD-score** is attributed to Pugh, Soros, Szerlip & Stanley, GECCO 2015, "Confronting the Challenge of Quality Diversity" (DOI 10.1145/2739480.2754664). That paper also studies how the quality measure aligns with the behavior characterization. — [UCF STARS record](https://stars.library.ucf.edu/scopus2015/2084). In later QD literature, QD-score is the sum of the best fitness in each filled cell, with empty cells counted as 0. Fitness is often offset to be non-negative or normalized. — [search-result summaries of QD papers, e.g. arXiv 2406.03731](https://arxiv.org/pdf/2406.03731). I did not read Pugh 2015's own definition.
- Pugh, Soros & Stanley 2016 (Frontiers in Robotics and AI 3:40) show that a single behavior characterization "is not necessarily sufficient for generating both quality and diversity at the same time." They propose combining several BCs in one run. — [Frontiers abstract](https://public-pages-files-2025.frontiersin.org/journals/robotics-and-ai/articles/10.3389/frobt.2016.00040/text)
- The DEI paper (ICML 2026 SCALE workshop) reports merged-archive QD-Score and coverage for LLM-driven QD on Core War. — [arXiv 2605.27130](https://arxiv.org/abs/2605.27130)

**Entropy and spectral measures**
- **HSEvo SWDI:** cluster programs greedily. A program joins a cluster only if its cosine similarity to every member is at least α = 0.95. Then compute H = −Σ p_i log p_i with p_i = |C_i|/M. **CDI:** build a minimum spanning tree on Euclidean embedding distances and compute the entropy of the normalized edge lengths. Neither index is normalized by design. SWDI is meaningful only within a run, not across runs. — [HSEvo](https://arxiv.org/html/2412.14995)
- **HSEvo correlation evidence:** in single ReEvo runs on bin packing (BPO), SWDI and CDI "correlate noticeably" with objective score, and a low-CDI run could not escape a local optimum. Across frameworks, though, EoH had the highest CDI (BPO 5.86, TSP 5.81, OP 6.17) but the worst objectives on BPO (3.17) and TSP (1.09). ReEvo and FunSearch had lower CDI and better objectives (ReEvo: BPO 2.48, TSP 0.05; FunSearch: BPO 2.05, TSP 0.09; lower is better). On OP, higher CDI went with a better objective. — [HSEvo](https://arxiv.org/html/2412.14995)
- **Vendi score:** "the exponential of the Shannon entropy of the eigenvalues of a similarity matrix" built from a user-defined similarity function. It needs no reference dataset. — [Friedman & Dieng, arXiv 2210.02410](https://arxiv.org/abs/2210.02410)
- In the classical GP literature, Burke et al. compared entropy-type phenotypic measures with structural ones. — [Burke et al. 2004](https://gpbib.cs.ucl.ac.uk/gp-html/gustafson_2004_IEEE.html)

**Correlation with success in LLM evolution**
- In the trajectory analysis, novelty measures had coefficients near zero, were not statistically significant, and had negligible explanatory power for final performance. Strong optimizers acted as local refiners that progressively localize in semantic space. Weak optimizers drifted, with sporadic breakthroughs followed by stagnation. Novelty helped only when search stayed localized around high-performing regions. — [arXiv 2604.19440](https://arxiv.org/abs/2604.19440); [HTML](https://arxiv.org/html/2604.19440)
- EvoLattice argues the opposite emphasis: internal, persistent diversity, with several alternatives stored per functional node, "is a decisive factor" in LLM-guided search. — [arXiv 2512.13857](https://arxiv.org/html/2512.13857). This summary comes from search results; I did not read the full paper.

### Inferences
- Both Burke 2004 and DivEval 2026 say text or structure diversity and behavior diversity separate. That supports the team's plan to measure diversity of eviction decisions rather than code text. FunSearch's score-signature clustering is the closest published precedent for a cheap behavioral signature.
- Vendi equals n when all items are mutually dissimilar (K = I) and 1 when all are identical. This follows from the definition, so it reads as an "effective number of distinct policies." With a Hamming-agreement kernel on eviction-decision vectors, it gives an interpretable behavioral count.
- No metric has robust evidence of correlating with final quality across tasks. HSEvo's own cross-framework table contradicts its within-run correlation, and the trajectory paper finds novelty non-predictive. Diversity metrics should therefore be reported next to quality, not used as a stand-alone quality proxy.

### Gaps
- DivEval's numbers (correlations, the "near-optimal region" widths) are not public in what I could access.
- VendiEvolve's exact signal (Vendi over which embedding or kernel) and its quantitative results were not in the public abstract.
- I found no study that measures behavioral diversity of cache replacement policies, or of any systems policy, discovered by LLM evolution.
- I did not read the Mouret & Clune or Pugh 2015 full texts, so their metric definitions are second-hand.

## Key Question 2: Process metrics specific to LLM evolution, and who reports them

### Takeaway
Process-health metrics are under-reported. AlphaEvolve, FunSearch, ShinkaEvolve, ReEvo and CodeEvolve report component ablations and sample counts, but none reports validity rate, duplicate rate or per-child improvement rate in the material I read. The richest process instrumentation is the LLaMEA/Leiden line of work and the OpenEvolve evolution trace. The LLaMEA line has diff ratios, mutation-rate adherence, code evolution graphs and behavior-space analysis. The OpenEvolve trace has improvement deltas and an improvement_rate statistic.

### Cited Findings
- **FunSearch (Nature 2024):** incorrect programs are discarded: time or memory overruns, or invalid output. The fraction is not reported in the main text. Islands are reset every 4 h: the worst half are wiped and reseeded with the best program of a random surviving island. For robustness, "every single run" beat the baseline on admissible sets and bin packing, 60% of I(12,7) runs found a full-size admissible set, and only 4 of 140 n=8 cap-set runs found a 512-cap. Runs drew about 10^6 samples, with 15 samplers and 150 CPU evaluators. Prompts with k = 2 programs beat k = 1, with diminishing returns beyond that. — [Romera-Paredes et al., Nature 2024](https://www.nature.com/articles/s41586-023-06924-6)
- **AlphaEvolve:** the ablations were no evolution, no prompt context, no meta-prompt evolution, no full-file evolution, and a small base LLM only. They ran on tensor decomposition and kissing number, and "each of the components is responsible for a significant improvement." Results appear only as plots of performance against compute (3 seeds). The program database combines MAP-Elites and island models. The mixture of LLMs is used "to obtain highly diverse samples." No validity or improvement rates are given. — [arXiv 2506.13131](https://arxiv.org/html/2506.13131)
- **ShinkaEvolve:** reports ablations of parent selection, novelty rejection and the bandit LLM ensemble. It describes evolution trees qualitatively. It does not report valid fraction, rejection rate or improvement rate. Invalid patches are resampled up to 3 times with Reflexion-style feedback. — [arXiv 2509.19349](https://arxiv.org/html/2509.19349)
- **ReEvo:** reports component ablations on TSP100 ACO (lower is better). Full method 8.40 ± 0.02 (white-box); LLM-only 8.64 ± 0.13; without long-term reflections 8.61; without short-term reflections 8.46; without crossover 8.45; without mutation 8.83. It also reports a fitness-landscape statistic: short-term reflection raised correlation length from 0.28 ± 0.07 to 1.28 ± 0.62. It reports no validity, duplicate or diversity statistics. — [arXiv 2402.01145](https://arxiv.org/html/2402.01145)
- **HSEvo:** reports SWDI and CDI trajectories, and CDI per framework for EoH, ReEvo and FunSearch. — [arXiv 2412.14995](https://arxiv.org/html/2412.14995)
- **CodeEvolve:** reports LLM calls needed to beat AlphaEvolve on circle packing n=26: about 900 with Qwen3-Coder-30B versus about 400 with Gemini-2.5. It also gives cost per run and topology and inspiration ablations. Only the cycle island topology beat AlphaEvolve at n=32, and 2–3 inspirations beat depth-only prompting. It computes no explicit validity or diversity metrics, and reports best and worst of 3 runs instead of standard deviation. — [arXiv 2510.14150](https://arxiv.org/html/2510.14150v3)
- **LLaMEA line (Leiden):**
  - Parent–offspring diff ratio. — [arXiv 2405.20132](https://arxiv.org/pdf/2405.20132)
  - Adherence to requested mutation rates of 2–40%, scored by log-ratio MSE. GPT-3.5-turbo "fails to adhere to the specific mutation instructions," while GPT-4o adapts. — [arXiv 2412.03250](https://arxiv.org/pdf/2412.03250)
  - Code Evolution Graphs. — [arXiv 2503.16668](https://arxiv.org/abs/2503.16668v1)
  - Behaviour-space analysis: per-candidate exploration, exploitation, convergence and stagnation, plus Search Trajectory Networks. The best variant was a 1+1 elitist strategy with simplify and random-perturbation prompts, and better performers showed more intensive exploitation and less stagnation. — [arXiv 2507.03605](https://arxiv.org/abs/2507.03605v1)
  - BLADE benchmark suite. — [arXiv 2504.20183](https://arxiv.org/abs/2504.20183)
- **Trajectory analysis (Findings of ACL 2026):** uses frequency of incremental improvement and semantic localization or drift as process descriptors. Good optimizers make frequent small improvements. — [arXiv 2604.19440](https://arxiv.org/abs/2604.19440)
- **Validity and error rates in other studies:**
  - LLM-GP (Hemberg, Moskal & O'Reilly, GPEM 2024) reports error rates per LLM operator. Selection had the highest error rate, mutation produced very few errors, and initialization produced none. — [MIT open-access PDF](https://dspace.mit.edu/bitstream/handle/1721.1/156878/10710_2024_Article_9494.pdf?sequence=1&isAllowed=y)
  - irace-evo reports a 13.33% compilation error rate (4 of 30 variants) for one configuration, and says small models produce more compile errors. — [arXiv 2511.14794](https://arxiv.org/pdf/2511.14794)
- **KV-cache eviction policies via OpenEvolve v0.5.1** (Poudel, Wu, Jha & Liu, arXiv 2608.14555; the closest domain analog). The runs used 3–12 islands, populations of 200–600 and 100–1,500 iterations, with a cascade evaluator. The paper reports reward hacking several times. In one case a mutation dropped a `[-k:]` slice so the candidate returned all indices. Runs B-Redux-2 and B-Redux-3v2 were marked "reward-hacked; fixed", and run v3b hacked again at iteration 1264. Four "diversity-controlled" runs from one seed "all stayed within the V1 family". The paper reports no validity, duplicate, improvement-rate or decision-level diversity numbers. A search-result summary states that about 100% of mutator output passes the syntax and import check while about 30–40% passes a later calibration stage. That figure came from a search snippet and was not re-checked in the HTML. — [arXiv 2608.14555 HTML](https://arxiv.org/html/2608.14555)
- **"Large Language Models as Evolution Strategies"** (Lange, Tian & Tang) uses an LLM as a recombination operator for numeric black-box optimization (BBOB and small neuroevolution). It is not program search, and the abstract has no diversity or process metrics. — [arXiv 2402.18381](https://arxiv.org/abs/2402.18381)
- **Evidence that the evolutionary loop matters:** a benchmark of four LLM-based evolutionary program search methods across 4 AHD problems, 9 LLMs and 5 runs "provide[s] empirical support for the importance of evolutionary search" (Zhang et al., PPSN 2024). — [arXiv 2407.10873](https://arxiv.org/abs/2407.10873)
- **OpenEvolve's tracer** computes `improvement_rate` and per-metric `total_improvement`, `best_improvement` and `worst_decline`, based on `combined_score`. Details are in KQ5. — [evolution_trace.py @ v0.4.0](https://raw.githubusercontent.com/algorithmicsuperintelligence/openevolve/v0.4.0/openevolve/evolution_trace.py)

### Inferences
- A useful process panel can be assembled from what different groups report. Its parts would be validity (build/run) rate, no-op or duplicate rate, improvement rate (child better than parent), improvement-delta distribution, novelty-rejection rate, LLM calls or tokens to reach X% of best, lineage depth of the best program, and per-island best and migrant success. No single published system reports all of them.
- Published LLM-evolution validity numbers are scarce and not comparable across languages or harnesses. One C++ build-and-simulate pipeline (irace-evo) gives 13%, and it is the only C-family figure I found. There is no external benchmark for whether a 15% build/run failure rate or a 24% copy/duplicate rate is normal.
- The KV-cache OpenEvolve study suggests reward hacking should be a tracked process metric for eviction-policy search, for example a count of programs flagged by an evaluator-contract check.

### Gaps
- I found no paper that reports a duplicate or identical-to-parent rate for LLM mutation.
- EoH (ICML 2024) process metrics were not checked.
- I did not read the AlphaEvolve and FunSearch supplementary appendices, which hold the ablation numbers.
- ELM / OpenELM validity rates were not checked.

## Key Question 3: Mode collapse and convergence in LLM-driven evolution

### Takeaway
Several 2026 papers document collapse. In DivEval, the retained population contracts while the generator stays varied. EvoDiverse reports "systematic diversity collapse", and HoliDivEvolve reports cross-island convergence. These papers measure collapse with embedding or lexical pairwise similarity, cluster counts, or cross-island overlap. No paper gives a base-rate frequency across runs. The remedies with measured gains are diverse or heterogeneous LLM ensembles, diverse seeding, embedding novelty rejection, parallel tempering across temperatures, and adaptive island selection. Raising temperature alone did not help in the one test I found.

### Cited Findings
- **DivEval temporal lens:** "the generator keeps producing varied candidates, while the retained population contracts into a high-retention, low-novelty state." Collapse is located in selection and retention, not generation. — [NeurIPS 2026 workshop listing](https://neurips.cc/virtual/2026/175781)
- **EvoDiverse (arXiv 2606.10587):** claims "systematic diversity collapse across a wide range of scientific discovery problems" caused by selection pressure. It measures diversity as mean pairwise CodeBERT cosine distance (equations) or TF-IDF distance (circle packing). On circle packing, diversity was EA 0.61, island model 0.48, isolated ensemble 0.76 and EvoDiverse 0.78; best sum of radii was 2.5461 versus 2.4986 for the plain EA. For molecules, about 50 diverse candidates at convergence for the baseline versus about 90. Raising temperature without swaps ("Tempering") underperformed the baseline on JNK3 Top-10 AUC (0.46 vs 0.58). The remedy is cold and hot pools with Metropolis–Hastings swaps, targeting a 30–50% swap rate. Gains are not uniform: equation-diversity margins are small and GSK3β Top-10 average was not best. — [arXiv 2606.10587 HTML](https://arxiv.org/html/2606.10587v1)
- **HoliDivEvolve (arXiv 2610.38407)** measures cross-island convergence with four metrics: best-program similarity, population proximity, exact code overlap and descendant proximity, all from shingle-Jaccard. On Signal Processing, max–min diverse initialization lowered best-program similarity from 0.183 to 0.062, population proximity from 0.424 to 0.086, and exact overlap from 0.183 to 0.000. Final scores were same-start 0.700, random 0.682 and max–min 0.714. Island selection with migration off: round-robin 0.628, uniform 0.645, UCB 0.633, adaptive 0.659. Baselines were OpenEvolve, ShinkaEvolve and AdaEvolve. The paper does not test novelty filters, temperature or ensembles. — [arXiv 2610.38407](https://arxiv.org/html/2610.38407)
- **ShinkaEvolve novelty rejection:** embed the mutable code (text-embedding-3-small). If the maximum cosine similarity to the island exceeds η = 0.95, ask an LLM judge whether the program is meaningfully different, with up to 3 attempts. On circle packing, embedding rejection gave "substantial performance gains" over no rejection, and the LLM-judge stage gave only "marginal improvements." No numbers are in the text. Weighted parent selection, sigmoid(performance) × 1/(1+N_children), beat both hill-climbing (which plateaus) and random selection. — [arXiv 2509.19349](https://arxiv.org/html/2509.19349)
- **Model ensembles:**
  - DEI's heterogeneous 4-LLM ensemble reached QD-Score 45.90 versus 20.46 for a single node at equal call budget, and coverage of 80.6% versus 63.0%. It also beat an equal-budget homogeneous ensemble. — [arXiv 2605.27130](https://arxiv.org/abs/2605.27130)
  - Code Evolution Graphs found that different LLMs write stylistically different code, and suggest that multi-LLM evolution may perform better. — [arXiv 2503.16668](https://arxiv.org/abs/2503.16668v1)
  - ShinkaEvolve's UCB1 bandit ensemble beat a single LLM. The text says "significantly", but the figure caption says only "slightly" better than a fixed ensemble. — [arXiv 2509.19349](https://arxiv.org/html/2509.19349)
- **The ensemble ceiling:** "Artificial Hivemind" (NeurIPS 2025 best paper, 70+ models) documents within-model repetition and, even more, inter-model homogeneity on open-ended prompts. Model ensembles therefore buy less diversity than their count suggests. — [NeurIPS 2025 oral](https://neurips.cc/virtual/2025/oral/121422); [arXiv 2510.22954](https://arxiv.org/abs/2510.22954v1)
- **Temperature:** for code generation, temperature above 1.0 raises algorithmic diversity but can reduce correctness. — [arXiv 2503.00691](https://arxiv.org/abs/2503.00691). See also EvoDiverse's negative result for temperature alone, above.
- **Diverse seeding / archives:** LEVI uses CVT-MAP-Elites with a diverse seed set. Removing diverse seeding reduced achievable performance and caused archive stagnation, especially on multi-family tasks. LEVI also claims to beat frontier-model runs of OpenEvolve, ShinkaEvolve, AdaEvolve and EvoX at 3.3–6.7× lower cost; these are author claims. — [arXiv 2605.09764](https://arxiv.org/abs/2605.09764); [project page](https://ttanv.github.io/levi/)
- **Islands:**
  - FunSearch resets the worst half of islands every 4 h. — [Nature 2024](https://www.nature.com/articles/s41586-023-06924-6)
  - In CodeEvolve, only the cycle topology beat AlphaEvolve at n=32. — [arXiv 2510.14150](https://arxiv.org/html/2510.14150v3)
  - In EvoDiverse's circle-packing table, the island model had the lowest diversity (0.48). — [arXiv 2606.10587](https://arxiv.org/html/2606.10587v1)
- **VendiEvolve** uses label-free distributional diversity signals to "diagnose population-level collapse" and to keep semantically distinct programs in the mutation context. On circle packing these signals "complement existing heuristics and improve final performance". No numbers are public. — [ICML 2026 listing](https://icml.cc/virtual/2026/68548)
- **Family lock-in:** in the KV-cache OpenEvolve study, four diversity-controlled runs from one seed stayed within the seed's family. The authors attribute the V2–V3 plateaus to the seed family, not to the iteration budget. — [arXiv 2608.14555](https://arxiv.org/html/2608.14555)
- **Checking embedding diversity:** in label-free LLM self-improvement (EVOL-RL), embedding cosine similarity was checked against an LLM judge. High-similarity pairs were judged the same 77.2% of the time, and low-similarity pairs were judged different 90.6% of the time. — [arXiv 2509.15194](https://arxiv.org/html/2509.15194). A separate study argues that embedding similarity may overstate homogeneity compared with human judgments. — [arXiv 2611.01549](https://arxiv.org/html/2611.01549). Both are search-summary level.

### Inferences
- DivEval found that the generator stays varied while the retained set collapses. That points to the archive and selection step as the place to measure collapse. In OpenEvolve terms, compare diversity of all children produced per window with diversity of the population or elites retained.
- Remedies with quantitative support (DEI, HoliDivEvolve, EvoDiverse, LEVI ablations) mostly change where search starts or which models generate. Remedies that only raise sampling randomness (temperature) have weak or negative evidence.
- Default OpenEvolve islands may not prevent collapse. In EvoDiverse an island model had the lowest diversity, and HoliDivEvolve found cross-island convergence when islands start from the same seed.

### Gaps
- No study reports how often collapse occurs as a fraction of runs, or gives a standard collapse threshold.
- ShinkaEvolve's novelty-rejection gains have no numbers in the text.
- No remedy evaluation uses C++ or systems-policy search.

## Key Question 4: Is diversity a goal or a diagnostic?

### Takeaway
Classical open-endedness work treats behavioral diversity, or novelty, as a goal in deceptive problems: stepping stones do not resemble the objective. Recent LLM-evolution evidence mostly supports treating diversity as a calibrated diagnostic, because too much diversity tracks drift and worse results. The best-supported position combines the two. Use behavioral (not textual) diversity, target a task-dependent band, and always report it next to quality. Textual and embedding diversity are easy to inflate.

### Cited Findings
- **For diversity as a goal:**
  - Lehman & Stanley (Evolutionary Computation 19(2):189–223, 2011): searching for behavioral novelty alone significantly outperformed objective-based search on a deceptive maze. Objectives can fail to reward the stepping stones that lead to the goal. — [GP bibliography](https://gpbib.cs.ucl.ac.uk/gp-html/Lehman_2011_EC.html); [PDF](https://www.cs.swarthmore.edu/~meeden/cs81/f17/papers/lehman_ecj11.pdf)
  - The same authors' book "Why Greatness Cannot Be Planned" (2015) generalizes this argument. — [Project MUSE](https://muse.jhu.edu/article/608610)
  - FunSearch states that "preserving and encouraging diversity" is crucial to avoid local optima. — [Nature 2024](https://www.nature.com/articles/s41586-023-06924-6)
  - HSEvo: increasing diversity improved ReEvo runs, and low CDI trapped search in a local optimum. — [arXiv 2412.14995](https://arxiv.org/html/2412.14995)
  - EvoLattice: persistent internal diversity is "decisive". — [arXiv 2512.13857](https://arxiv.org/html/2512.13857)
  - DEI: heterogeneous ensembles improved QD-Score and held-out generality. — [arXiv 2605.27130](https://arxiv.org/abs/2605.27130)
  - EvoDiverse argues its diversity is "productive". — [arXiv 2606.10587](https://arxiv.org/html/2606.10587v1)
  - VendiEvolve frames the population as information about "how the search behaves, where it fails, and what alternatives exist". — [ICML 2026](https://icml.cc/virtual/2026/68548)
- **For diversity as a diagnostic, or calibrate rather than maximize:**
  - DivEval: near-optimal diversity regions depend on the task and measurement level, so diversity should be calibrated, not maximized. — [NeurIPS 2026 workshop](https://neurips.cc/virtual/2026/175781)
  - Trajectory analysis: novelty has no significant predictive power, high novelty often signals operators that "drift across semantic space without refining promising solutions", and strong LLM optimizers are local refiners. — [arXiv 2604.19440](https://arxiv.org/html/2604.19440)
  - HSEvo's cross-framework data: EoH had the highest CDI but the worst objective on BPO and TSP, which the authors call too little exploitation. — [arXiv 2412.14995](https://arxiv.org/html/2412.14995)
  - Behaviour-space analysis: the best LLaMEA variant was 1+1 elitist with more intensive exploitation. — [arXiv 2507.03605](https://arxiv.org/abs/2507.03605v1)
  - EvoDiverse's own ablation: higher temperature without swaps (more randomness) did worse. — [arXiv 2606.10587](https://arxiv.org/html/2606.10587v1)
- **Task dependence:**
  - The sign of the CDI–objective relationship flipped between OP and BPO/TSP in HSEvo. — [arXiv 2412.14995](https://arxiv.org/html/2412.14995)
  - Burke 2004: the diversity–fitness correlation varies over the run, and "diversity might have different meaning for different problem domains". — [GP bibliography](https://gpbib.cs.ucl.ac.uk/gp-html/gustafson_2004_IEEE.html)
  - Pugh 2016: one behavior characterization may not align with quality. — [Frontiers](https://public-pages-files-2025.frontiersin.org/journals/robotics-and-ai/articles/10.3389/frobt.2016.00040/text)
  - Pugh et al. PPSN 2016 studied QD "when diversity is unaligned with quality" (title-level only; not read). — [UCF STARS](https://stars.library.ucf.edu/scopus2015/4548)
- **Gaming and inflation risk:**
  - DivEval's weak code-to-behavior coupling implies that textual novelty can be raised without functional change. — [NeurIPS 2026 workshop](https://neurips.cc/virtual/2026/175781)
  - Embedding-based spread measures, Vendi included, share a core limitation: "although the context can be structurally similar, the semantics can be very different". This quote comes from a search-result summary, and I could not confirm which paper it belongs to. The likeliest source is a 2026 paper that uses Vendi in a task-embedding space. Treat the attribution as unverified. — [arXiv 2604.14969 (attribution uncertain)](https://arxiv.org/pdf/2604.14969)
  - Embedding similarity may overstate homogeneity. — [arXiv 2611.01549](https://arxiv.org/html/2611.01549)
  - Evaluator gaming happens in practice in OpenEvolve eviction-policy search (repeated reward hacks). — [arXiv 2608.14555](https://arxiv.org/html/2608.14555)
  - OpenEvolve's built-in "diversity" feature is a character, line and length difference: `length_diff * 0.1 + line_diff * 10 + char_diff * 0.5`, compared against a 20-program reference set. — [database.py @ v0.4.0](https://raw.githubusercontent.com/algorithmicsuperintelligence/openevolve/v0.4.0/openevolve/database.py)

### Inferences
- OpenEvolve's text-diversity score rewards line-count and character changes. Adding comments, renaming or reformatting would move a program to a new MAP-Elites cell without changing eviction behavior. This is a concrete inflation path, and a reason not to use that feature as an evaluation metric.
- Behavioral diversity over eviction decisions resists that inflation, since cosmetic edits produce identical decision vectors. It can still be gamed: a policy that makes arbitrary but harmless different choices, for example tie-breaking among equally cold lines, inflates decision-level diversity without changing hit rate. Pair it with a performance-profile level, such as per-trace miss or IPC vectors, which is DivEval's fourth level.
- Behavioral diversity fits as a secondary criterion and diagnostic. Compare configurations on quality at equal budget, then use diversity to explain differences and to detect collapse. Rewarding diversity directly is unsupported for single-objective tuning. It has better support for deceptive problems or when a portfolio of policies is the deliverable.

### Gaps
- I found no direct study of diversity gaming in LLM-evolution metrics. The inflation argument above is my inference from the metric definitions.
- No empirical study maps diversity to success for cache or systems policies specifically.

## Key Question 5: Which metrics can be computed from OpenEvolve 0.4.0's records, and what built-in tools exist?

### Takeaway
OpenEvolve 0.4.0 checkpoints store each program's code, parent_id, generation, iteration_found, metrics, the parent's metrics, island and prompts. That is enough to compute improvement rate, lineage depth and stepping stones, per-island statistics, MAP-Elites coverage and QD-score, and any genotypic or behavioral diversity (behavioral by re-running stored code on a recorded access stream). Rejected iterations are not stored: parse failures, over-length code and rewrites identical to the parent appear only in the run log. Inspirations are not recorded. The repo ships a Flask lineage visualizer (`scripts/visualizer.py`) and an evolution-trace module that is off by default but can be extracted retroactively from checkpoints.

### Cited Findings
- **The Program record** has `id`, `code`, `changes_description`, `language`, `parent_id`, `generation`, `timestamp`, `iteration_found`, `metrics`, `complexity`, `diversity`, `metadata`, `prompts`, `artifacts_json`, `artifact_dir` and `embedding`. There is no top-level island field: the island is in `metadata["island"]`. — [database.py @ v0.4.0](https://raw.githubusercontent.com/algorithmicsuperintelligence/openevolve/v0.4.0/openevolve/database.py)
- **Child metadata** is set in the worker as `"changes"`, `"parent_metrics": parent.metrics`, `"island": parent_island` and `"token_usage"`. Inspiration ids are not recorded. `metadata["island"]` is the parent's island, while placement uses `result.target_island`. — [process_parallel.py @ v0.4.0](https://raw.githubusercontent.com/algorithmicsuperintelligence/openevolve/v0.4.0/openevolve/process_parallel.py)
- **Checkpoints** write one `programs/<id>.json` per program. `metadata.json` holds island assignments, archive, feature maps, best-program ids, `last_iteration`, `current_island`, island generations, migration state and `feature_stats`. When `log_prompts` is on (default True), prompts are attached to programs. — [database.py](https://raw.githubusercontent.com/algorithmicsuperintelligence/openevolve/v0.4.0/openevolve/database.py); [config.py @ v0.4.0](https://raw.githubusercontent.com/algorithmicsuperintelligence/openevolve/v0.4.0/openevolve/config.py)
- **Rejected iterations are not stored.** The worker returns errors such as "No valid code found in response", "Generated code exceeds maximum length", "Rewrite is identical to the parent program" (full-rewrite mode) and "Diff did not change the parent program" (diff mode). The controller logs these as `Iteration N error: ...` warnings and adds nothing to the database. Children rejected by `database.add` returning None are logged at INFO as "Admission strategy rejected program %s". Admitted children are logged as "Iteration N: Program X (parent: Y) completed in …s" followed by all metrics. — [process_parallel.py](https://raw.githubusercontent.com/algorithmicsuperintelligence/openevolve/v0.4.0/openevolve/process_parallel.py)
- **Evaluation failures:** if the evaluator returns metrics, for example a zero score with an error flag, the child is stored with those metrics. If it raises, nothing is stored. The only duplicate check is against the parent; nothing compares a child with the rest of the database. — [process_parallel.py](https://raw.githubusercontent.com/algorithmicsuperintelligence/openevolve/v0.4.0/openevolve/process_parallel.py)
- **Migrants** are stored as copies with `metadata={..., "island": target_island, "migrant": True}` and `parent_id` pointing to the source. By default the top `migration_rate` fraction moves to two ring neighbours. — [database.py](https://raw.githubusercontent.com/algorithmicsuperintelligence/openevolve/v0.4.0/openevolve/database.py)
- **Default database config:** `feature_dimensions: ["complexity","diversity"]`, `feature_bins: 10`, `num_islands: 5`, `migration_interval: 50`, `migration_rate: 0.1`, `archive_size: 100`, `population_size: 1000`, `elite_selection_ratio: 0.1`, `exploration_ratio: 0.2`, `exploitation_ratio: 0.7`, `diversity_reference_size: 20`, `similarity_threshold: 0.99`, `embedding_model: None`, `novelty_llm: None`. `diversity_metric` is listed as `"edit_distance"`, which is inconsistent with the actual fast text formula. Prompt defaults are `num_top_programs: 3` and `num_diverse_programs: 2`. — [config.py @ v0.4.0](https://raw.githubusercontent.com/algorithmicsuperintelligence/openevolve/v0.4.0/openevolve/config.py)
- **Built-in feature definitions:** "complexity" is `len(program.code)`, binned. "diversity" is the mean `_fast_code_diversity` against a greedily chosen reference set of up to 20 programs. An evaluator metric with the same name as a dimension overrides the built-in, so custom behavioral descriptors can be fed straight into the MAP-Elites grid. The novelty filter, when configured, compares embeddings within the same island only, asks `novelty_llm` for "NOVEL" or "NOT NOVEL", and defaults to novel on parse errors. — [database.py](https://raw.githubusercontent.com/algorithmicsuperintelligence/openevolve/v0.4.0/openevolve/database.py)
- **Logged statistics:** `get_island_stats()` gives per-island `population_size`, `best_score`, `average_score`, `diversity`, `generation` and `is_current`. Logs also record MAP-Elites cell occupation, replacements, coverage milestones (10/25/50/75/90%), migrations and population-cap removals. — [database.py](https://raw.githubusercontent.com/algorithmicsuperintelligence/openevolve/v0.4.0/openevolve/database.py)
- **Evolution trace** (`openevolve/evolution_trace.py`): config `evolution_trace.enabled` defaults to **False**, with format jsonl, json or hdf5, `include_code` False and `include_prompts` True. Each record has iteration, parent_id, child_id, generation, island_id, parent_metrics, child_metrics, improvement_delta, and optionally code, prompt and llm_response. `get_statistics()` returns `improvement_count` and `improvement_rate` on `combined_score`. Only admitted children are traced. — [evolution_trace.py](https://raw.githubusercontent.com/algorithmicsuperintelligence/openevolve/v0.4.0/openevolve/evolution_trace.py); [config.py](https://raw.githubusercontent.com/algorithmicsuperintelligence/openevolve/v0.4.0/openevolve/config.py); [process_parallel.py](https://raw.githubusercontent.com/algorithmicsuperintelligence/openevolve/v0.4.0/openevolve/process_parallel.py)
  - It works retroactively. `extract_evolution_trace_from_checkpoint(checkpoint_dir)` builds parent→child traces from `programs/*.json`. `extract_full_lineage_traces(checkpoint_dir)` walks each `parent_id` chain to the root, with metric deltas, change descriptions and the first prompt and response, sorted deepest first. — [evolution_trace.py](https://raw.githubusercontent.com/algorithmicsuperintelligence/openevolve/v0.4.0/openevolve/evolution_trace.py)
- **Visualizer** (`scripts/visualizer.py`): a Flask app. Point it at an output dir or a `checkpoint_*` folder with `--path`, plus `--host`, `--port` and `--static-output DIR` for a standalone HTML export. It reads `metadata.json` and `programs/*.json`. `/api/data` returns nodes and parent→child edges (the lineage tree) and the archive. `/program/<id>` shows code, prompts, metrics and artifacts. Code-level caveats: `--static-output` does not exit as documented, and `/program/<id>` fails until `/api/data` has been called. — [visualizer.py @ v0.4.0](https://raw.githubusercontent.com/algorithmicsuperintelligence/openevolve/v0.4.0/scripts/visualizer.py)
- **Repo tree at v0.4.0:** `openevolve/evolution_trace.py`, `openevolve/utils/trace_export_utils.py`, `openevolve/novelty_judge.py`, `openevolve/embedding.py`, `scripts/visualizer.py`, `scripts/manual.py`, and tests such as `test_evolution_trace.py`, `test_migration_no_duplicates.py` and `test_prompt_inspiration_dedup.py`. There is no dedicated diversity-analysis or plotting script outside examples. — [GitHub tree @ v0.4.0](https://api.github.com/repos/algorithmicsuperintelligence/openevolve/git/trees/v0.4.0?recursive=1)
- A newer OpenEvolve release, v0.5.1, existed by Aug 2026. One study using it describes its MAP-Elites axes as "program complexity and code-embedding diversity". — [arXiv 2608.14555](https://arxiv.org/html/2608.14555)

### Inferences
Each metric below is computable from what 0.4.0 stores.
- **Improvement rate** (fraction of children better than their parent): directly from `metrics.combined_score` against `metadata.parent_metrics.combined_score` in `programs/*.json`. Exclude records with `metadata.migrant == True`. Alternatively run `extract_evolution_trace_from_checkpoint` on existing checkpoints and use the tracer's statistics. The denominator then counts only stored children; a per-LLM-call rate also needs the logged errors.
- **Validity rate:** build and run failures are visible only if the evaluator returns a failure metric rather than raising. Parse, over-length and identical-to-parent outcomes must be counted from the log lines (`Iteration N error: ...`). The full validity funnel is: LLM calls → parsed → non-identical → under length cap → evaluated without exception → admitted. It needs both the logs and the checkpoint.
- **Duplicate rate:** identical-to-parent outcomes come from logs only. Duplicates of non-parent programs can be counted from stored code: hash normalized code, stripping comments and whitespace, or use TSED with a threshold. Migrant copies must be excluded, or they will inflate duplicates.
- **Lineage depth and stepping stones:** `generation` gives depth directly, and `parent_id` chains give the ancestry of the best program. A stepping-stone analysis can ask how many ancestors of the final best were never island-best or elite, or ranked below the population median when created. All of this uses `iteration_found` and stored metrics.
- **Island effects:** per-island best and mean over iterations, from `metadata.island` and `iteration_found`. Migrant success is the share of descendants of migrant copies that improve. Because `metadata.island` holds the parent's island, the island assignments in `metadata.json` are safer for placement.
- **QD coverage, QD-score and archive size:** from the feature maps and archive in `metadata.json`, and from the logged coverage milestones. On the default grid these measure text features, not behavior. Swapping in evaluator-returned behavioral features is supported, because a metric with the same name as a feature dimension overrides the built-in.
- **Inspiration and context use:** not recorded as ids. It can be reconstructed only by matching inspiration code blocks inside the logged `prompts` text against stored program code, and is approximate.
- **Behavioral diversity** (eviction decisions): not stored, since it needs re-running each stored program's code. One caveat for the method: a replacement policy's decisions change the future cache state, so free-running decision streams diverge after the first difference. A common-state protocol avoids this: replay a fixed access stream through a reference policy's cache states and record each candidate's counterfactual victim choice. Per-trace miss or IPC vectors (a FunSearch-style signature) give the complementary performance-profile level. A Hamming-agreement Vendi score, or SWDI over behavior clusters, can then be computed per checkpoint, for both all children and retained elites, to look for DivEval-style retention collapse.

### Gaps
- I did not read `trace_export_utils.py`, `novelty_judge.py`, `population.py` or `selection.py` at v0.4.0. The admission-strategy behavior behind "Admission strategy rejected program" is therefore not characterized.
- I did not check whether population-cap pruning (default 1000) or orphan removal deletes historical programs from later checkpoints. Pruning would bias lineage analysis on long runs. A short run of about 240 iterations should be under the cap.
- I did not verify that `programs/*.json` keeps `metadata.parent_metrics` for every program across save and load.
